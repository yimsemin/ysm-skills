# tidy-code

동작을 바꾸지 않고 코드·CSS·테스트를 더 짧고 단순하게 만든다. 큰 변경 뒤에는 요청이 없어도 한다.

## 허용과 금지

- **새 동작·기능 추가 금지**: 사용자가 보는 결과는 그대로여야 한다.
- **합쳐서 만드는 것은 허용**: 중복을 모아 새 공통 함수·컴포넌트·CSS 클래스·변수를 만들어도 된다. 단 합친 결과 전체 줄 수와 중복이 실제로 줄어야 한다.
- **금지**: 한 곳에서만 쓰는 추상화, 앞으로를 대비한 계층·옵션, 줄이는 효과가 없는 재구성.

## 1. 범위와 기준선

- 범위는 사용자가 준 곳이고, 없으면 최근 변경이 많았던 파일부터 본다.
- 정리 전에 테스트·빌드(`AGENTS.md`의 "실행과 검증")를 새로 실행해 통과를 확인한다. 이미 실패하면 정리하지 말고 보고한다. 명령이 없으면 기준선이 없다고 먼저 보고하고 범위를 줄인다.
- 미커밋 변경은 사용자 작업인지 확인하고 그 파일은 건드리지 않는다.

## 2. 점검

변경 전에 목록부터 만든다. 삭제 후보는 `grep`으로 참조 0건을 확인한 것만 올린다.

- **미사용**: 코드·CSS·의존성·파일·주석 처리된 코드.
- **중복**: 같은 로직, 값만 다른 CSS. 케이스마다 따로 붙은 CSS는 기본 구조 + 변형으로 합칠 수 있는지 본다.
- **구조**: 여러 일을 하는 큰 함수·파일, 깊게 얽힌 조건, 낡은 방식.
- **테스트**: 아래 3단계.

## 3. 테스트 검증

기존 테스트도 믿을 수 있어야 한다. 베이스라인 "코드와 테스트" 구역 기준으로 본다.

- **쓸모**: 극단 상황 가정, 다른 테스트와 같은 확인, 구현 세부에 묶인 것은 통합하거나 삭제 후보로 올린다.
- **신뢰**: 단언이 없거나 항상 통과하는 것, 건너뛴 것, 불안정한 것을 찾는다. 핵심 테스트는 대상 동작을 임시로 깨 보아 **실패하는지** 확인하고 즉시 원복한다. 미커밋 사용자 변경이 있으면 이 확인은 하지 않는다.
- 기대값을 현재 결과에 맞춰 고쳐 통과시키지 않는다.

## 4. 수정

묶음(미사용 삭제, 중복 통합, 구조, 테스트)마다 고치고 테스트·빌드를 새로 실행한다. 깨지면 그 묶음을 되돌리고 원인을 보고한다. 동작이 바뀔 수 있는 수정과 공개 인터페이스 변경은 결정 항목으로 남긴다. 커밋은 사용자가 요청할 때 묶음별로 한다.

## 5. 보고

"한 일 / 확인하지 못한 것 / 하지 않은 것"으로 나누고 결정 항목을 맨 위에 둔다. 줄어든 규모(파일·줄·테스트 수)와 전후 테스트·빌드 결과를 쓴다. 문자열로 조립하는 클래스명 같은 동적 참조는 "확인하지 못한 것"에 쓴다.
