# write-readme

README는 개발자용 설명서가 아니라 처음 온 사람을 위한 소개 페이지다. 낡은 정보·중복 정리는 `audit-docs`, 문서 위치와 단일 출처는 베이스라인 "문서" 구역이 맡는다. 이 스킬은 README의 정보 구조와 표현만 다룬다.

## 1. 첫 화면 기준

첫 화면(스크롤 없이 보이는 범위)이 방문자의 세 질문에 답한다.

1. **이게 뭐지?** 한 줄로 정체성과 대상(누구의 어떤 일).
2. **나한테 필요한가?** 얻는 결과와 쓸 만한 상황. 기능 목록이 아니라 "그래서 나에게 무엇이 좋은가"로 쓴다.
3. **어떻게 쓰지?** 주 사용자에게 가장 쉬운 시작 하나.

신뢰는 실제 화면·실제 사용 예·현재 상태 표기로 준다. 수식어("간편한", "강력한")는 근거가 없으면 쓰지 않는다.

## 2. 쓰기 전 확인

- 주 사용자 유형을 정한다: 웹앱 / 에이전트 도구 / 앱·일반 도구 / 개발자 라이브러리·CLI. 복합형이면 일반 사용자 경로를 먼저 쓴다.
- 코드·`AGENTS.md`·`docs/`·기존 README를 읽되 근거로만 쓴다. 코드에서 찾은 기능마다 "그래서 사용자에게 무엇이 좋은가" 한 문장으로 답하고, 답하지 못하면 README에서 빼거나 `docs/`로 보낸다. 코드 구조 소개는 쓰지 않는다.
- 목적·대상이 코드로 알 수 없으면 사용자에게 한 번에 묶어 묻는다.

## 3. 쓰기

- **시작 방법**: 웹앱은 주소, 에이전트 도구는 저장소 주소가 든 복사용 요청문, 앱은 설치처, 라이브러리·CLI는 설치와 최소 실행. 직접 실행해 확인한 명령만 쓴다.
- **상태 구분**: 지금 되는 것과 예정인 것을 나눠 표기한다. 예정은 사용자 말·로드맵·이슈에 있는 것만 쓰고, 확인하지 못한 동작은 쓰지 않는다.
- **시각 자료**: 실제 화면·GIF만 쓴다. 필요한데 없으면 만들어 넣지 말고 "필요한 이미지" 목록으로 알린다. 배지·로고는 정보가 될 때만 쓴다.
- **뒤로 보낼 것**: 설치 환경, 개발·빌드·배포, 구조, 기여 방법은 첫 화면 뒤에 두거나 `docs/`로 링크한다. 개인 컴퓨터 정보와 비밀값은 쓰지 않는다.
- 제작 배경·경위보다 사용자가 얻는 가치를 쓴다. 기존 언어 정책과 다국어 사본이 있으면 따르고 함께 맞춘다.

## 4. 기존 README 개선

처음에는 구성을 크게 바꿔도 된다. 먼저 첫 화면이 세 질문 중 무엇에 답하지 못하는지 진단해 보고하고, 검증된 내용·링크·이미지는 보존한다. 이후 유지보수는 바뀐 부분만 고친다. 개선 요청 없이 README 전체를 다시 쓰지 않는다.

## 5. 자체 검수

- 첫 화면만 보고 세 질문에 답할 수 있는가. 모르는 사람 기준으로 소리 내어 읽어 본다.
- 길이가 필요 이상 늘지 않았는가. 확인하지 않은 기능·수치·명령이 없는가.
- 링크·이미지 경로가 실제로 있는가. 렌더링(`gh`·브라우저)을 볼 수 있으면 한 번 본다.

## 6. 보고

사용자가 결정할 항목(필요한 이미지, 확인하지 못한 사실, 예정 기능 표기)을 맨 위에 두고, 첫 화면 세 질문에 어떻게 답하는지와 "한 일 / 확인하지 못한 것 / 하지 않은 것"을 쓴다. 커밋은 사용자가 요청할 때 한다.
